# Лабораторная работа №2. Параллельное умножение квадратных матриц (OpenMP)

## 1. Описание алгоритма

### 1.1 Порядок обхода i-k-j

Стандартный алгоритм умножения матриц C = A × B выглядит следующим образом:

```
C[i][j] = Σ(k=0..N-1) A[i][k] * B[k][j]
```

В данной реализации используется оптимизированный порядок циклов **i-k-j**:

```cpp
for (int i = 0; i < n; ++i) {
    for (int k = 0; k < n; ++k) {
        double a_ik = A[i * n + k];
        for (int j = 0; j < n; ++j) {
            C[i * n + j] += a_ik * B[k * n + j];
        }
    }
}
```

**Особенности и преимущества i-k-j**:

* Внутренний цикл по `j` обращается к элементам `B[k][j]` и `C[i][j]` последовательно в памяти, что обеспечивает высокую эффективность работы процессорного кэша.
* Значение `A[i][k]` вынесено во временную переменную, что исключает лишние обращения к памяти.
* Несмотря на оптимизацию, при достижении больших значений N матрицы перестают помещаться в кэш-память, что ведет к падению производительности.

### 1.2 Вычислительная сложность

* **Количество математических операций**: **2N³** (N³ умножений и N³ сложений).
* **Сложность по памяти**: **3N²** элементов типа `double` (каждый по 8 байт). Память является общей для всех потоков, дублирование данных не требуется.

## 5. Анализ результатов

### 5.1 Ускорение и влияние гибридной архитектуры (P/E cores)

Теоретически, при идеальном распараллеливании ускорение должно расти линейно и равняться количеству потоков (S = T). На практике полученное ускорение на 12 потоках составило ~7.9x. Это объясняется двумя факторами:

1. **Насыщение (Memory Wall):** С увеличением количества потоков до 8 (и более), рост производительности часто перестает быть линейным из-за того, что узким местом становится пропускная способность оперативной памяти (ПСП), а не вычислительные мощности ядер. Ядра процессора простаивают в ожидании данных из ОЗУ.
2. **Гибридная архитектура:** Процессор i5-1240P состоит из 4 производительных ядер и 8 энергоэффективных. Добавление в пул вычислений E-ядер дает меньший удельный прирост производительности по сравнению с полноценными P-ядрами, что ведет к постепенному снижению КПД.

### 5.2 Влияние кэша в многопоточной среде

При параллельном выполнении каждый поток активно загружает свои фрагменты матриц A, B и C в кэш своего ядра (L1/L2). При больших размерах N матрицы перестают помещаться даже в общий L3 кэш, что вызывает лавину кэш-промахов (cache misses) и задержек при обращении к ОЗУ. Из-за этого графики производительности (GFLOP/s) для всех конфигураций потоков показывают выраженный пик на малых-средних матрицах (N=400..800) и постепенный спад при N=1600+.

### 5.3 Накладные расходы на малых матрицах (Накладные расходы OpenMP)

При размерах задачи N=200 использование многопоточности оказалось неэффективным. Время работы 1 потока составило 0.0026 сек, а 12 потоков — 0.0027 сек. Это связано с тем, что накладные расходы операционной системы на создание, синхронизацию и управление 12 потоками превышают выгоду от разделения столь малого объема вычислений.

## 6. Выводы

1. Программа успешно модифицирована для работы в многопоточном режиме с использованием технологии OpenMP.
2. Использование директив OpenMP позволяет достичь кратного увеличения производительности при минимальном вмешательстве в исходный код.
3. Практически доказан закон Амдала и влияние накладных расходов: распараллеливание имеет смысл только для задач достаточно большого объема (в данном случае N > 400).
4. Максимальная зафиксированная производительность составила ~32.18 GFLOP/s (при N=800 на 12 потоках), в то время как последовательная версия выдавала около 3-5 GFLOP/s.
